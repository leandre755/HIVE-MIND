# Why HIVE-MIND TUI Uses a Decoupled WebSocket Client-Server Architecture

## The Concurrency and Lifespan Problem

Initially, the HIVE-MIND terminal interface was executed in the same process thread as the agent's Core operations. This setup led to two severe problems:

1. **Thread blocking**: When the agent performed heavy synchronous tasks (like processing code ASTs or downloading large media chunks), the React-Ink terminal rendering thread froze, preventing the spinner from animating and causing keystroke lag.
2. **Process vulnerability**: If the terminal renderer crashed due to an unhandled layout overflow or window resizing error, the entire agent Core would go down with it, interrupting background tasks and socket listeners (like WhatsApp connections).

---

## Architectural History and Alternatives

Historically, command-line agents compiled their interface alongside the program logic. To fix the process coupling, three main designs were evaluated:

| Architectural Approach              | Pros                                                                                         | Cons                                                                                        |
| ----------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Direct Process Shared Library**   | Simple setup, fast memory share.                                                             | A crash in the terminal layout kills the Core.                                              |
| **Child Process Spawning (stdio)**  | Isolated processes.                                                                          | Standard streams (`stdin`/`stdout`) get polluted by random plugin `console.log` statements. |
| **Local WebSocket Bridge (Chosen)** | True process isolation; clean separate debug boundaries; supports remote client TUI control. | Slight serialization latency (typically < 1ms on localhost).                                |

---

## How the WebSocket Bridge Resolves the Issue

By migrating to a client-server architecture via local WebSockets (`ws://127.0.0.1:5001`), the Core and TUI client run as distinct node processes:

1. **Separation of Concerns**: The Core acts as a headless WebSocket server that registers event handlers and writes configuration settings token files (`tui-connection.json`).
2. **Async Resiliency**: If the TUI client crashes, the Core keeps running. The client automatically attempts reconnection loops in the background until the socket recovers.
3. **Secure Handshake**: A dynamic uuid token generated by the server at boot ensures that only the local client instance can connect to the Core API.

---

## Architectural Perspective

Decoupling terminal rendering from process core execution is a crucial step towards SOTA agent engineering. In command-line applications, UI rendering is often considered secondary and bound directly to the main script. However, since modern agentic frameworks rely on state preservation (such as long-term DB sync and persistent WhatsApp sockets), the UI must be treated as a disposable viewport.

While WebSockets introduce minor complexities regarding token handshakes and port availability, the absolute protection of the agent's main thread justifies this design choice.
