## 🧠 Decisions Made

- [2026-08-07] **Unification du shutdown via SIGTERM (session WhatsApp persistence)**
- **Context**: Trois chemins d'arrêt du bot (Ctrl+C SIGINT, `shutdown_bot` dev_tools, `os_shutdown` plugin) n'assuraient pas le flush de `creds.json` avant `process.exit()`. `os_shutdown` et `shutdown_bot` appelaient directement `process.exit(0)` dans un `setTimeout`, contournant la chaîne de cleanup de `hive-mind.ts`. Résultat : perte de session WhatsApp après arrêt/restart.
- **Discarded Options**: Flush explicite dans chaque handler (rejeté : duplication de la chaîne SIGTERM déjà complète dans `hive-mind.ts`) ; `await saveCreds()` global partout (rejeté : ne couvre pas le disconnect socket ni le releaseLock).
- **Rationale**: (1) `shutdown_bot` et `os_shutdown` appellent désormais `process.kill(process.pid, 'SIGTERM')` → déclenche le handler SIGTERM de `hive-mind.ts` → flush DB → saveCreds → disconnect → releaseLock → exit. (2) Le handler `shutdown()` isole chaque étape dans son propre try/catch pour qu'une erreur n'empêche pas les suivantes. (3) `sendPresenceUpdate` wrappé dans un try/catch interne dans `baileys.ts disconnect()` pour garantir que `sock.end()` est toujours exécuté. (4) `whatsappAuthHelper.ts` catch : suppression conditionnelle de `session/` uniquement si `!state.creds.registered` (préservation sur erreur transitoire). Validation : `tsc` 0, `eslint` 0/0, audit invariants 5/5 PASS.

- [2026-08-06] **Retrait du QR code automatique du transport Baileys (suppression du doublon avec le menu)**
- **Context**: Le transport `baileys.ts connect()` affichait un QR code automatiquement au démarrage du bot core si aucune session valide n'existait — comportement hérité d'avant l'ajout du menu `startupMenu`. Avec le menu interactif qui pilote désormais l'authentification (QR ou pairing code au choix via `whatsappAuthHelper`), ce QR auto devenait un doublon : il se déclenchait quand l'utilisateur skip le menu sans connexion, ou en mode headless/Railway où le menu est skippé automatiquement, affichant un QR inutilisable en mode serveur.
- **Discarded Options**: Conserver le QR auto comme secours Railway (rejeté : un QR dans les logs Railway ne peut être scanné, c'est du bruit — l'auth se fait via le menu en TTY local une fois pour toutes) ; retirer aussi l'option QR du sous-menu (rejeté : l'utilisateur a explicitement demandé de garder le menu avec l'option QR, seul le comportement auto à l'ancienne est visé) ; retirer la définition `QR_RECEIVED` de `events.ts` (rejeté : hors scope, fichier adjacent non strictement nécessaire, la définition morte est inoffensive).
- **Rationale**: (1) Retrait de l'import `qrcode`, `printQRInTerminal:true`→`false`, branche `if (qr)` et champ `qr` supprimés dans `_handleConnectionUpdate`. (2) Guard `if (!state.creds.registered) throw` dans `connect()` → échec propre avec message clair si le transport démarre sans session, au lieu d'un QR mort. (3) `QR_RECEIVED` n'avait aucun subscriber (publish déjà mort). (4) L'option QR du sous-menu `startupMenu` + le mode QR de `whatsappAuthHelper` RESTENT intactes (auth pilotée par l'utilisateur). Les reconnexions 515/440 passent le guard (`creds.registered` reste `true`). Validé statiquement (tsc/eslint/499 tests).

- [2026-08-06] **Gestion du Restart 515 (`restartRequired`) post-pairing WhatsApp**
- **Context**: Après validation du code pairing sur le téléphone, `creds.update` passe `registered` à `true`, PUIS WhatsApp ferme la connexion avec le statut 515 (`DisconnectReason.restartRequired`). C'est un comportement normal du protocole multi-device : le socket DOIT être recréé pour finaliser la session authentifiée. L'ancienne logique `handleConnectionClose` ne reconnectait QUE si `pairingRequested && !isRegistered` — au moment du 515 `registered===true` → aucune branche exécutée → aucun nouveau socket → attente d'un `connection==='open'` impossible → timeout 120s → « impossible de se connecter à cet appareil ». Confirmé par la lecture du dépôt de référence Toxic-MD (`index.js:1101`) qui gère explicitement le 515 dans sa clause de reconnexion via `startToxic()` sans condition sur `registered`.
- **Discarded Options**: Ignorer le 515 et augmenter le timeout (rejeté : le socket est mort, aucun `open` n'arrivera jamais quelle que soit la durée) ; traiter le 515 comme un `loggedOut`/fail (rejeté : le 515 est un restart attendu après succès pairing, pas une déconnexion réelle) ; ne reconnecter que sur `reason===515` explicite (rejeté : `isRegistered` couvre le cas nominalement sans dépendre d'un code raison spécifique fragile face aux variantes de Baileys).
- **Rationale**: Ajout d'une branche `if (isRegistered) { setTimeout(onReconnect, 1500); return; }` dans `handleConnectionClose` avant les autres conditions. À la reconnexion via `startSock()`, le guard `mode==='pairing' && !pairingState.requested && !state.creds.registered` (l.253) devient faux → aucun redemande de code → le nouveau socket se connecte directement avec les creds authentifiées → `connection==='open'` + `isRegisteredLive()` → `finish(true)`. Validation runtime utilisateur : connexion réussie.

- [2026-08-06] **Flush disque explicite de `creds.json` pour fiabiliser la détection UI**
- **Context**: Après `finish(true)` (connexion réussie), le menu principal relit immédiatement `session/creds.json` via `isWhatsAppConnected()` (exige `registered===true && me.id`). Or le dernier `creds.update` (contenant `me.id`) est persisté de façon asynchrone par le listener `saveCreds` — au moment du rendu du panneau, le flush disque n'était pas terminé → lecture d'un `creds.json` incomplet → faux « 🔴 DÉCONNECTÉ » alors que la session était valide. Vérifié empiriquement : post-connexion, `creds.json` contient bien `registered:true` + `me.id`.
- **Discarded Options**: Ajouter un `delay` fixe avant le rendu menu (rejeté : les règles interdisent les delay fixes pour les race conditions async, préférer les signaux explicites) ; poller `creds.json` jusqu'à ce que `me.id` apparaisse (rejeté : complexité inutile, le flush awaited résout la course à la source).
- **Rationale**: Dans `finish`, sur succès uniquement, appel `await saveCreds()` AVANT `resolvePromise(result)`. `saveCreds` sérialise l'état courant en mémoire (`state.creds`, déjà muté par Baileys à l'open) vers le disque de façon awaited → garantit qu'au retour du menu, `creds.json` est complet. `finish` devient async interne (`void finalize()`) sans casser l'API `Promise<boolean>`. Les anciens faux positifs (« connecté » alors qu'échec) déjà couverts par la détection stricte `registered===true && me.id`.

- [2026-08-06] **Correction du Bug use-after-delete ENOENT `session/creds.json`**
- **Context**: `useMultiFileAuthState` (Baileys v6.7.23) crée le dossier `session/` puis n'écrit `creds.json` qu'au premier événement `creds.update` (post-pairing). Or `whatsappAuthHelper.ts` appelait `disconnectWhatsApp()` (→ `safeRemoveDirectorySync`) 3 lignes après l'init quand `registered===false` (toujours vrai en première auth), supprimant le dossier avant l'écriture → `ENOENT` au moment où l'utilisateur saisit le numéro pour recevoir le code. Gap secondaire : `baileys.ts connect()` n'assurait jamais le dossier avant l'appel (échec sur volume Railway vide).
- **Discarded Options**: Migration vers `useSqliteAuthState` (rejeté : refactoring majeur hors scope, `useMultiFileAuthState` déprécié mais fonctionnel) ; purge conditionnelle anticipée avec lecture/parsing de `creds.json` (rejeté : ajoute de la logique de parsing sans bénéfice, la suppression du bloc suffit) ; simple `safeMkdirSync` sans supprimer le bloc purge (rejeté : le dossier était re-supprimé juste après).
- **Rationale**: (1) `safeMkdirSync(WA_SESSION_DIR, {recursive:true})` idempotent AVANT `useMultiFileAuthState` dans `whatsappAuthHelper.ts` et `baileys.ts`. (2) Suppression totale du bloc use-after-delete `if (!state.creds.registered) { disconnectWhatsApp(); }` (lignes 210-212) — la purge propre reste garantie par `finish()` (après retrait des listeners) et `catch()`. (3) `authSessionManager.ts` non modifié (déjà robuste). Réutilisation des wrappers `safeFs.ts` existants, imports ESM `.js`.

- [2026-08-06] **Validation Réseau en Direct des Jetons & Correction de l'Architecture de Couplage Baileys**
- **Context**: 1. `requestPairingCode` Baileys échouait avec HTTP 428 (`Connection Closed`) si le numéro était demandé dans l'événement du socket (timeout de connexion en arrière-plan pendant la saisie humaine) et si le `browser` était un tuple personnalisé inconnu de WhatsApp. 2. - **Discarded Options**: Conserver la saisie du numéro dans l'événement socket avec un timer d'attente (rejeté : le socket expire pendant la saisie de l'utilisateur) ; utiliser un tuple de browser libre (rejeté : WhatsApp bloque les pairings non reconnus).
- **Rationale**: (1) Demande synchrone du numéro de téléphone de manière découpée *avant* l'instanciation de `makeWASocket()`. (2) Utilisation du signature `Browsers.ubuntu('Chrome')` natif de Baileys. (3) Validation réseau en direct via requêtes `fetch` sécurisées par `AbortSignal.timeout(8000)` auprès de l'API Telegram (`/getMe`) et Discord (`/users/@me`) avant tout enregistrement dans `.env`. (4) Nettoyage des dossiers de session par les wrappers sûrs `safeRemoveDirectorySync` de `safeFs.ts`.
